1Introduction

Before optimizing a kernel, an engineer should be able to answer three questions about it. What limits its speed? How far is it from that limit? And what kind of change could still make it faster? This chapter develops a model that answers all three, the roofline model of Williams, Waterman, and Patterson [5].

The model is built in steps. Section 2 introduces the two hardware limits: how fast a GPU computes and how fast it moves data. Sections 3 to 5 use them to bound a kernel's running time, derive arithmetic intensity, and draw the roofline. Sections 6 and 7 measure four kernels on an NVIDIA B200 and explain where they fall, and Section 8 shows how the roofline guides optimization.

Objectives

After studying this chapter you should be able to predict, from a kernel's operation and byte counts, whether it is limited by compute or by memory; place a measured kernel on the roofline; and explain, for a kernel below its roof, why it is there and how it could improve.

2The Hardware: Two Limits

Every kernel consumes two resources: arithmetic, performed by the processors, and data, delivered by the memory system. This section describes where each comes from on a GPU and gives the maximum rate of each on the B200.

2.1Streaming multiprocessors and warps

A GPU consists of a number of streaming multiprocessors (SMs), each an independent processor with its own registers, scheduler, and arithmetic units. The B200 exposes 148 SMs to software. A program for the GPU, called a kernel, is launched as a grid of thread blocks, which the hardware distributes among the SMs as resources allow (Figure 2.1). Within an SM, threads are scheduled in groups of 32 called warps, all threads of a warp executing the same instruction at the same time (Figure 2.2).

2.2Peak compute

Each SM contains general-purpose arithmetic units, called CUDA cores, and tensor cores, specialized units that perform small matrix multiplications at much higher throughput. The peak compute throughput P is the largest number of floating-point operations the device can complete per second. It depends strongly on the data type and on the unit used (Figure 2.3): on an A100, for example, tensor cores complete four times as many FP16 multiply-adds per cycle as CUDA cores.

For dense BF16 matrix arithmetic on tensor cores, NVIDIA gives P ≈ 2.25 PFLOP/s (2.25 × 1015 operations per second) for the B200. This is the figure used in this chapter. Arithmetic on CUDA cores has a much lower peak, a point to which Section 3 returns.

2.3The memory hierarchy and peak bandwidth

Data reaches the SMs through a hierarchy (Figure 2.4): registers and an L1 cache on each SM, a 126 MB L2 cache shared by all SMs, and device memory (HBM3e DRAM) behind it. Each level is larger and slower than the one above it. The peak memory bandwidth B is the largest number of bytes per second that can move between device memory and the chip. Nsight Compute, NVIDIA's kernel profiler, reports the peak for our device as 1.92 kB per DRAM cycle at 3.995 GHz, that is B ≈ 7.67 TB/s. In this chapter “bandwidth” means DRAM bandwidth, counting both reads and writes.

3A First Bound on Time

The two limits of Section 2 are enough to bound the running time of any kernel. Suppose a kernel performs W floating-point operations and moves Q bytes between DRAM and the chip. Even if nothing else delayed it, the arithmetic alone would take at least W/P seconds, and the data alone at least Q/B. A GPU can compute and move data at the same time, so the two may overlap, but the kernel cannot finish before the longer of them:

T ≥ max(W/P, Q/B)(3.1)

Whichever term is larger names the resource that limits the kernel. If Q/B is larger the kernel is memory-bound; if W/P is larger it is compute-bound.

Example 3.1 A gated residual

Our first kernel, case 1 of this chapter, computes y = x + g[k] ⊙ b over 32,768 rows of 5,376 BF16 elements, 1.76 × 108 elements in all. It is a simplified version of an operation in the MiniMax-H3 video diffusion model, the gated residual connection at the end of each transformer block. Each token is a row of 5,376 values. x is the token's row before the block (the residual stream), b is what the block's attention or MLP layer computed for it, and g is a small table of 12 gate rows, of which row k applies to this token. The symbol ⊙ denotes element-wise multiplication, so the gate scales the block's output channel by channel before it is added back: with three channels, x = (1, 2, 3), b = (0.5, 0.5, 0.5) and g[k] = (1, 0, 2) give y = (1.5, 2, 4). Each element needs one multiplication and one addition, so W = 2 × 1.76 × 108 = 3.5 × 108 operations. Each element requires reading one value of x and one of b and writing one of y, 2 bytes each; the gate g[k] is a row of a small table that stays in the L2 cache and costs no DRAM traffic. So Q = 6 × 1.76 × 108 = 1.06 × 109 bytes.

The arithmetic bound is 3.5 × 108 / 2.25 × 1015 ≈ 0.16 µs; the data bound is 1.06 × 109 / 7.67 × 1012 ≈ 138 µs. The data bound is nearly a thousand times larger, so the kernel is memory-bound and cannot run in less than 138 µs. The conclusion does not depend on which compute peak is used: element-wise kernels run on CUDA cores, whose peak is far below 2.25 PFLOP/s, but even a peak a hundred times lower would leave the arithmetic bound under 20 µs.

Case 2, an RMS normalization followed by an affine modulation over the same elements, performs about 6 operations and moves 4 bytes per element. Its bounds are 0.47 µs for arithmetic and 92 µs for data, so it too is memory-bound.

4Arithmetic Intensity

4.1The deciding ratio

In both examples the data term of Equation 3.1 was the larger. The data term exceeds the arithmetic term when Q/B > W/P, which rearranges to W/Q < P/B. The left side depends only on the kernel; the right side depends only on the hardware. The kernel's side is its arithmetic intensity:

I = WQ = floating-point operationsbytes moved to and from DRAM(4.1)

and the hardware's side is the ridge point:

Iridge = P / B(4.2)

A kernel with I < Iridge is memory-bound and one with I > Iridge is compute-bound. The question of Section 3 therefore reduces to comparing two numbers. For the B200, Iridge = 2.25×1015 / 7.67×1012 ≈ 293 FLOP/byte: a kernel must perform almost 300 operations for every byte it moves before arithmetic becomes its limit.

Intensity is a property of the algorithm and its data layout, not of the hardware. The bytes counted are those that cross the DRAM boundary: a value read once from DRAM and then reused from cache is counted once, and data that stays in cache is not counted at all. For case 1, I = 2 operations / 6 bytes ≈ 0.33 FLOP/byte; for case 2, I ≈ 6/4 = 1.5. Both are two to three orders of magnitude below the ridge point.

These values are typical. Table 4.1 reproduces NVIDIA's examples for common neural-network operations. Activations, pooling and normalization, like cases 1 and 2, sit near or below 10 FLOP/byte. A linear layer, which is a matrix multiplication, behaves differently: its intensity depends on the batch size.

4.2Matrix multiplication

Multiplying an M × K matrix by a K × N matrix requires 2MKN operations and, at a minimum, reading both inputs and writing the M × N output once each, 2(MK + KN + MN) bytes in BF16. Its intensity is therefore

I = MKNMK + KN + MN(4.3)

Cases 3 and 4 of this chapter are matrix multiplications of the kind performed at each decode step of a large language model: M tokens, each a vector of K = 8,192 values, are multiplied by a weight matrix of 8,192 × 28,672 BF16 values, 470 MB in all. When M is much smaller than K and N, the weight term KN dominates the denominator of Equation 4.3 and I ≈ M. Case 3, with a single token, has I ≈ 1.0 FLOP/byte, no higher than an element-wise kernel. Case 4, with 4,096 tokens, has I ≈ 2,493 FLOP/byte by Equation 4.3. The same operation spans three orders of magnitude of intensity and lies on opposite sides of the ridge point, depending only on the batch size.

All of these values rest on a model of the bytes moved, which assumes that every input is read from DRAM exactly once. Section 6 checks the model against measurement.

5The Roofline

5.1From a bound on time to a bound on performance

Performance is operations per second, W/T. Dividing W by both sides of Equation 3.1, and using W/Q = I, gives an upper bound on performance:

Attainable performance = min(P, I × B)(5.1)

Equation 5.1 is the roofline model. The term I × B has a direct reading: the memory system delivers B bytes per second, and the kernel performs I operations on each, so data can sustain at most I × B operations per second. The two terms are equal at the ridge point of Equation 4.2. Equation 5.1 is an upper bound; it assumes the kernel uses its limiting resource perfectly, and every real kernel lies on or below it. 5.2Drawing the roofline

The roofline is drawn with intensity on the horizontal axis and performance on the vertical axis, both on logarithmic scales. On such axes the bound I × B is a straight line: a tenfold increase in I gives a tenfold increase in performance, and both appear as equal distances. Changing B moves the line up or down without changing its slope. The bound P is a horizontal line. The two meet at the ridge point, and together they form the roof. Logarithmic axes are needed because kernels span many orders of magnitude; our four cases cover intensities from 0.3 to over 2,000.

Figure 5.1 draws the roofline of the B200 with the four cases at the positions predicted in Table 5.1.

NVIDIA's profiler draws the same chart for a measured kernel. Figure 5.2 shows it as Nsight Compute presents it. The sloped line is labelled the memory bandwidth boundary, the horizontal line the peak performance boundary, and the dot the kernel's achieved value. Nsight Compute draws one horizontal line for each floating-point precision, which is why the figure has two.

Example 5.1 Reading Figure 5.2

At the left edge of the chart the bandwidth boundary passes through about 0.5 GFLOP/s at an intensity of 0.001 FLOP/byte, so the device in the figure has B = 0.5 / 0.001 = 500 GB/s. The lower ridge point lies near 0.6 FLOP/byte at about 300 GFLOP/s, and 300 / 500 = 0.6 confirms Equation 4.2. The dot is at 0.04 GFLOP/s, about 0.3 percent of its roof; the table above the chart reports the kernel's DRAM utilization as 0.34 percent, in agreement.

6Measuring a Kernel's Position

6.1Three measurements

A prediction places a kernel on its roof; a measurement shows where it actually is. To place a kernel on the chart we need its operations, its bytes, and its time. Achieved intensity is operations ÷ bytes, and achieved performance is operations ÷ time. Nsight Compute measures the time and the DRAM bytes directly, in the metrics gpu__time_duration.sum, dram__bytes_read.sum, and dram__bytes_write.sum. It also counts executed floating-point instructions, from which it computes operations for its own roofline chart.

That count must be used with care. For cases 3 and 4 the profiler's BF16 tensor-operation counters read zero, although the tensor cores were 73 to 82 percent busy: the counters do not cover the instructions these Blackwell GEMM kernels use, and Nsight Compute's own chart would place both GEMMs near zero. In this chapter, therefore, operations are counted from the algorithm, and only time and bytes are measured.

For cases 1 to 3 the measured reads agree with the model to within a megabyte: each input element is read from DRAM once, and the small tables of cases 1 and 2 are served from L2, as assumed. The measured writes of cases 1 and 2 fall 30 to 43 MB short of the model. L2 is a write-back cache, and when a kernel ends the last part of its output is still held there; it reaches DRAM later, after the measurement has closed. The 4 MB written by case 3 are partial sums: cuBLAS splits the long K dimension across thread blocks and adds the parts in a second, small kernel.

Case 4 departs from the model. It reads 1,601 MB, three times the minimum. Its two inputs, 67 MB and 470 MB, cannot be held in the 126 MB L2 together, so the GEMM fetches parts of them from DRAM more than once. Its measured intensity is therefore 1.92×1012 operations ÷ 1.83×109 bytes ≈ 1,050 FLOP/byte, not 2,493. The kernel remains far to the right of the ridge point, so the prediction that it is compute-bound still holds, but the model overstated its intensity by a factor of more than two.

7Explaining the Measured Positions

Intensity explains each point's regime but not its distance below the roof. That requires two ideas the roofline does not contain: latency and occupancy.

7.1Case 1: on the roof

The gated residual runs at 86 percent of its roof, moving 6.62 TB/s. For comparison, a plain device-to-device copy, a kernel that does nothing but read and write, reaches 6.19 TB/s on the same device when timed outside the profiler. Case 1 is therefore at the practical limit of the memory system. Its arithmetic does not matter, since its arithmetic units are only 36 percent busy, and its memory access can hardly be improved. The roofline's verdict on this kernel is that further optimization in isolation is not worthwhile.

7.2Case 2: latency, concurrency, and occupancy

Case 2 has a slightly higher intensity than case 1, and so a higher roof, yet it delivers less: 3.20 TB/s, or 42 percent of its roof. It is memory-bound but does not use the memory system fully.

Bandwidth is the rate at which data can flow; latency is the time a single request takes to be answered. A load that misses in the caches travels from the SM to DRAM and back, a trip of several hundred nanoseconds whatever the size of the request. At 7.67 TB/s, by contrast, the 16 bytes a thread may request in one instruction take a small fraction of a nanosecond to transfer. For a single small load, nearly all the time is latency. Peak bandwidth can therefore be reached only if many requests are in flight at once. The required amount is given by Little's law from queueing theory:

Bytes in flight = Bandwidth × Latency(7.1)
Example 7.1 Bytes in flight on the B200

With B = 7.67 TB/s and an assumed latency of 600 ns, Equation 7.1 requires 7.67×1012 × 600×10−9 ≈ 4.6 MB in flight across the device, or about 31 KB on each of the 148 SMs. A kernel whose structure keeps less than this outstanding cannot reach the bandwidth peak, however little arithmetic it does.

The requests an SM keeps in flight come from the warps resident on it. The fraction of an SM's warp slots that are occupied is its occupancy, and it is limited by the resources each warp needs, chiefly registers: the register file of an SM is fixed, so the more registers each thread uses, the fewer warps fit. Nsight Compute's Launch Statistics and Occupancy sections show the consequence for case 2. The kernel assigns one program to each row and holds the entire 5,376-element row, padded to 8,192, in registers in order to compute the row's norm. This requires 74 registers per thread. At that usage only 37.5 percent of the SM's warp slots can be filled, and the kernel achieves 33 percent: about 21 warps per SM, against 55 for case 1. Too few warps are resident to keep enough loads in flight, and the memory system waits.

Occupancy is not the only source of requests in flight. A thread that issues several independent loads before using any of them keeps several requests outstanding by itself, and Volkov showed that this instruction-level parallelism can reach full bandwidth at low occupancy [6]. Case 2 cannot exploit it easily, because its norm must be complete before any output can be computed. Its position on the roofline is the visible consequence of a structural choice, and it identifies case 2 as the kernel with the most to gain, perhaps a factor of two before it reaches the level of case 1.

7.3Cases 3 and 4: one operation, two regimes

With one token, the matrix multiplication of case 3 runs at 85 percent of its memory roof, and its time is essentially the time to read the 470 MB weight: 470 MB ÷ 6.5 TB/s ≈ 73 µs. Its tensor cores are almost idle.

Why the intensity rises with the batch can be seen from how a GEMM is computed. The output is divided into tiles, each computed by one thread block, which steps through the K dimension loading a tile of each input at every step (Figure 7.1). An element of a weight tile, once loaded, is used for every row of the output tile. With one token there is only one row, so each weight element loaded from DRAM is used once; with many tokens it is used many times.

With 4,096 tokens the point moves to the compute side of the ridge, where it reaches 72 percent of the compute roof. Nsight Compute shows the transition from both sides: from case 3 to case 4, DRAM throughput falls from 85 to 20 percent of peak while SM throughput rises from 25 to 97 percent. The remaining gap to the compute roof is largely a matter of clock frequency: the roof assumes the boost clock, whereas under sustained tensor-core load the SMs ran at 1.39 GHz.

A sweep of intermediate batch sizes shows where the transition occurs (Figure 7.2). Up to M = 256 the time per multiplication stays between 78 and 101 µs, the time to read the weight, while the work grows 256-fold. Between M = 256 (intensity 246) and M = 512 (intensity 474), on either side of the ridge point of 293, the time begins to grow in proportion to M. Below the ridge point, therefore, adding tokens to a decode step costs almost nothing. This is the quantitative reason that inference servers batch the decode steps of many requests together.

8Using the Roofline to Decide

A kernel below its roof can be improved in two directions, and the roofline makes clear which is available.

8.1Moving up

A kernel can move up toward its roof by using the limiting resource more effectively without changing its intensity. For a memory-bound kernel this means more requests in flight, fewer wasted cycles, and fewer launches, with the same bytes. Case 1 is itself the product of such a change. An earlier version of the gate, which processed each row as a single tile of 8,192 elements, used 48 registers per thread and reached 50 percent occupancy and 76 percent of peak bandwidth. Splitting each row into three tiles of 2,048 elements reduced the registers to 32, raised occupancy to 86 percent and bandwidth to 86 percent of peak, and cut the time by 11 percent, while the bytes moved were identical. It was made in vLLM-Omni pull request #10857 for the MiniMax-H3 model.

8.2Moving right

A kernel can move right, to higher intensity, by doing the same work with fewer bytes. The usual means is fusion: combining kernels so that an intermediate result stays on chip instead of being written to DRAM and read back. Run separately, the gate of case 1 and the normalization of case 2 move 10 bytes per element, because the gate writes its output and the normalization reads it again; fused into one kernel they move 8. Bytes fell by 20 percent and time by 22 percent, from 393 to 307 µs, with identical output. Fusion raised the intensity from 0.8 to 1.0 FLOP/byte, but it did not lift the kernel to its roof: the fused kernel inherited the register pressure of case 2 and runs at 59 percent of peak bandwidth. Moving right and moving up are independent, and a kernel may need both. Figure 8.1 shows the two moves.

8.3Knowing when to stop

The roofline also says when to stop. A kernel near its roof, such as case 1 or case 3, cannot be made much faster in isolation; the remaining gains lie elsewhere, in fusing it with its neighbours or in reducing the work itself. And because a kernel occupies only part of a program's time, Amdahl's law limits what any single kernel can contribute: if a fraction f of the running time is accelerated by a factor s, the whole program is accelerated by 1 / ((1 − f) + f/s) [1, 2].

8.4What the roofline does not show

The roofline locates a kernel but does not explain it: case 2 needed occupancy data, and case 4 measured bytes. The model also assumes a single memory level and a single peak. A kernel limited by L2 bandwidth, by shared memory, or by instruction issue will appear below the DRAM roof for reasons the chart cannot show; Nsight Compute provides a hierarchical roofline, with one roof per memory level, for such cases. Finally, all four points were measured in isolation. Inside a full model, kernels compete for caches and power, and memory-bound kernels in particular run slower than they do alone.

9Summary

A kernel cannot run faster than either the device's peak compute P or its peak bandwidth B allows. Which limit applies depends on the kernel's arithmetic intensity I compared with the ridge point P/B, and the bound min(P, I × B), drawn on logarithmic axes, is the roofline. A measured kernel lies on or below it, and its distance below the roof is the opportunity. To close that distance a kernel can move up, by using the limiting resource better, or right, by moving fewer bytes.
